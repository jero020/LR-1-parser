## Features

### Language Specification

The language supports rule-based programming with the following grammar:

```
Program → RuleList
RuleList → Rule RuleList | ε
Rule → rule id : if Cond then Action
Cond → Cond AND Cond | Atom
Atom → id RelOp value | id
RelOp → > | < | =
Action → id
```

### Supported Constructs

- **Rules**: Named rules with conditions and actions
- **Conditions**: 
  - Numeric comparisons (`>`, `<`, `=`)
  - Fact conditions (identifier checks)
  - Conjunctions with `AND`
- **Actions**: Activation of facts
- **State**: Initial variables and facts

### Implementation Components

1. **Lexer** (`lexer.py`): Tokenizes source code into a stream of tokens
2. **Parser** (`parser.py`): Recursive descent parser that builds an AST
3. **AST Nodes** (`ast_nodes.py`): Data structures for the abstract syntax tree
4. **Interpreter** (`interpreter.py`): Executes rules with fixed-point iteration
5. **Static Analysis** (`static_analysis.py`): Detects:
   - Action conflicts (multiple rules generating the same fact)
   - Redundant rules (identical condition and action)
   - Potentially inactive rules (not applied during execution)

## Input Format

### Rules File

```
rule <id>:
if <condition> then <action>

rule <id>:
if <condition> then <action>
```

Rules are separated by blank lines. Keywords (`rule`, `if`, `then`, `AND`) are case-sensitive.

### State File

Variable assignments:
```
variable = integer
```

Active facts (one per line):
```
fact_name
```

### Example Rules

```
rule r1:
if temp > 30 then alert

rule r2:
if alert AND active then notify
```

### Example State

```
temp = 35
active
```

## Output Format

### Execution Output

- Derived facts are printed one per line in alphabetical order
- Each fact is printed at most once
- If no facts are derived, outputs: `(no output)`

### Static Analysis Messages

After execution output, analysis messages are printed:

- **Conflicts**: `Action <fact> generated by r1, r2, ...`
- **Redundancy**: `Redundant rules: r1, r2`
- **Inactive Rules**: `Potentially inactive rule: <id>`

## Algorithm

### Interpretation Strategy (Fixed-Point)

1. Initialize active facts from the initial state
2. Repeat until no new facts are added:
   - Evaluate all rules
   - For each rule with a true condition, collect its action
   - Add new facts to the active set
3. Return derived facts (excluding initial facts)

### Evaluation Rules

- `Cmp(x, op, v)`: True if variable x satisfies the comparison
- `Fact(x)`: True if x is an active fact
- `And(c1, c2)`: True if both c1 and c2 are true

## Design Decisions

1. **Recursive Descent Parser**: Chosen for clarity and maintainability despite the grammar not being LL(1). The implementation handles left recursion in the condition grammar.

2. **Separate Variable and Fact Tracking**: Variables maintain numeric values while facts are boolean states, allowing independent roles for identifiers.

3. **Fixed-Point Iteration**: Rules are evaluated repeatedly until reaching a fixed point (no new facts derived), ensuring deterministic results regardless of rule order.

4. **Static Analysis Filtering**: Redundant rules are excluded from "potentially inactive" reporting to avoid redundant warnings.
